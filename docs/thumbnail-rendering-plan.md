# Reliable slide thumbnails

Status: implemented. See [the rendering contract](thumbnail-rendering.md) for deck hooks and diagnostics. Immutable snapshots and dependency-based invalidation remain follow-up work.

## Goal and decision

Make the thumbnail strip show a useful, complete static view of every slide, including after AI edits that insert, delete, or reorder slides.

Keep image thumbnails, generated by a dedicated static rendering mode in a hidden browser renderer. Reuse a renderer for each settled content revision and cache its output. Preserve arbitrary HTML deck support.

Two concerns must be handled separately:

1. Define the static state a slide should show, independent of presentation animation timing.
2. Associate every rendered image with the correct slide and content revision.

Switching to live, scaled previews alone would not solve both concerns.

## Current implementation and findings

- `app/slide-thumbnails.tsx` lazily requests nearby previews in batches of up to six and stores images by slide index.
- `app/page.tsx` remounts the strip on revision changes and clears the slide count while the preview reloads.
- `electron/main.js` serializes thumbnail batches and cancels outstanding work on deck refresh. Project `generation` changes when opening or closing a project, but not on ordinary file edits.
- `electron/screenshot.js` creates a hidden 1280 × 720 browser window per batch, navigates between slides, waits for image decoding and fonts, then waits for two animation frames before capture. Thumbnail output is resized to 320 pixels wide.
- That preparation does not finish entrance animations, explaining incomplete content in thumbnails.
- `electron/pdf.js` already finishes finite browser animations, pauses repeating animations, and performs more extensive asset readiness checks. Extract reusable preparation behavior from this code.
- The reported repeated screenshot has not been reproduced or assigned a confirmed root cause. Investigate position-based identity, multi-file edits during loading, and navigation/paint readiness before assuming a cache bug.

## Proposed rendering contract

Introduce an explicit thumbnail context through the injected deck bridge. It must be separate from presentation playback and editing selection state.

Default static preparation should:

- Navigate to the requested slide and verify the intended slide is active.
- Wait for fonts, slide images, and relevant CSS image assets. Make lazy images eligible to load.
- Complete finite CSS and Web Animations after activation, including delayed entrance effects.
- Pause repeating motion at a useful representative state.
- Allow bounded additional preparation when finishing an animation triggers subsequent effects or content changes.
- Wait for layout and paint preparation before capture and check that the slide has visible dimensions.
- Bound readiness waits and return a per-slide failure without preventing navigation or successful previews for other slides.

Do not rely only on `animation: none`: disabling an animation can leave content in its hidden base style. Finishing every animation is also not universally correct; exit animations and mutually exclusive states need explicit handling.

Provide an optional deck hook for static preparation and readiness. Custom decks can use it to reveal click-driven content, settle JavaScript timers, draw a static canvas/chart, choose a video poster, or select a representative state. Define the hook's interface during implementation. Browser animation APIs alone cannot settle arbitrary JavaScript or interactive content.

For legacy decks, offer best-effort browser preparation with bounded waits. Preserve presentation behavior outside the thumbnail context.

## Revision and slide identity

Introduce a content revision distinct from project generation. Carry it through the slide manifest, thumbnail requests, readiness acknowledgements, cache keys, and capture results.

- Keep project generation for project lifecycle isolation.
- Invalidate pending capture work promptly when a relevant file change is observed. Schedule replacement work after changes settle.
- Accept a result only when its project, content revision, and requested slide identity still match the current manifest.
- Correlate navigation/readiness acknowledgements with a request token so an unrelated state message cannot satisfy a capture request.
- Use persistent slide IDs when the deck provides them. Use position only to order those IDs.
- Support legacy decks without persistent IDs by scoping index identity to one revision and invalidating the entire revision on changes.
- Never assign an old image to a new slide merely because it occupies the same index. While rebuilding, show placeholders unless an old preview can be safely associated with the same slide.

A revision token does not freeze files. AI edits may update HTML, CSS, JavaScript, and JSON across multiple saves. Begin with change settling, immediate invalidation, and a revision check before publishing results. If mixed-file reads remain a problem, render from an immutable revision snapshot. Snapshotting is a stronger, higher-complexity follow-up, not a guarantee provided by debouncing.

## Renderer and cache lifecycle

- Maintain one isolated hidden thumbnail renderer for the current settled revision, rather than loading the deck for every batch.
- Keep sandboxing, resource restrictions, and separation from the visible presentation preview.
- Serialize navigation and capture within that renderer.
- Prioritize visible thumbnails, then a small nearby buffer. Retain lazy generation rather than eagerly capturing the whole deck.
- Cache by project, content revision, slide identity, and rendering parameters such as output size.
- Bound cache memory and release renderer resources on project close, revision replacement, cancellation, or failure.
- Recover from a failed renderer without retaining images under incorrect identities.
- Keep the existing 320-pixel output initially; tune resolution only after measuring quality and cost.

Start with whole-revision invalidation. Shared styles, fonts, scripts, and assets can affect every slide, so selective invalidation requires dependency tracking. Add it only if measurements justify the complexity.

## Implementation sequence

1. **Reproduce and instrument.** Add focused fixtures for delayed animations and rapid insert/delete/reorder edits. Record requested revision, slide identity, navigation acknowledgement, active slide, and returned result to locate the repeated-image failure.
2. **Make capture identity reliable.** Add explicit content revisions and correlated readiness responses, reject stale work, and implement safe index fallback for legacy decks. Stable IDs can be supported without making them mandatory.
3. **Introduce static preparation.** Extract shared browser preparation from PDF export, add thumbnail context and the optional deck hook, and preserve existing PDF and presentation semantics.
4. **Reuse the renderer and cache images.** Add revision-scoped renderer ownership, cancellation, bounded caching, and per-slide error recovery while preserving lazy scheduling.
5. **Measure and refine.** Compare representative decks before introducing selective invalidation or immutable snapshots.

Keep each logical implementation change reviewable, validated, and committed according to the repository's Git workflow.

## Validation and acceptance criteria

Extend the existing thumbnail integration coverage and use visually distinct slide fixtures so repeated captures are detectable. An image URL changing is insufficient evidence that it shows the correct slide.

- Delayed and staggered entrance animations show intended static content without waiting for their real-time duration.
- Infinite animation does not block generation. Custom timer, canvas, and video fixtures demonstrate the deck hook and fallback behavior.
- Insert, delete, and reorder operations, including changes during a batch and changes that preserve slide count, never publish an image under another slide's identity.
- Multi-file saves cancel stale work and eventually produce previews for the settled revision.
- Rapid edits and project close/reopen do not allow old results into the current strip or leak renderer resources.
- A failing slide can show an unavailable preview while other slides render and navigation remains usable.
- Main-preview animation and editing behavior remain correct; PDF output retains its existing behavior.
- Lazy loading, filmstrip scrolling, keyboard navigation, and active-slide visibility continue to work.

Run the relevant existing checks, including `npm run test:thumbnails`, `npm run test:screenshot`, and `npm run test:pdf` when their paths change, plus unit tests and type checking appropriate to the implementation.

Measure time to first visible thumbnail, visible-strip completion, edit-to-preview latency, scrolling responsiveness, CPU usage, memory, renderer count, and repeated-edit resource growth. Use short and long decks with heavy images, fonts, charts, canvas, and animations. Establish baselines before setting numerical performance targets.

## Alternatives considered

| Approach | Performance and complexity | Assessment |
| --- | --- | --- |
| Improve the current per-batch screenshots | Cheap display; repeated deck startup. Low–medium implementation complexity. | Useful first step, with static preparation and identity fixes reusable in the proposed design. |
| Full-size iframe per visible thumbnail, visually scaled down | Avoids capture and encoding, but each mounted frame runs deck code and retains DOM state. Medium complexity. | Best alternative to prototype if eliminating image capture is a priority. Requires virtualization and static mode. |
| One shared iframe rendering an overview | Loads scripts once, but retains multiple slides and requires a new overview layout/bridge. High complexity. | Viable if the app adopts a stronger overview rendering contract. |
| Render or clone slides into the app DOM | Can be efficient for controlled components; difficult CSS, script, ID, canvas, and viewport compatibility. High–very high complexity. | Poor general fit for arbitrary HTML decks. |
| DOM-to-image libraries | Adds serialization or CSS reconstruction work and compatibility limitations. | Little advantage over Electron's native browser capture. |
| PDF-derived thumbnails | Cheap display but expensive regeneration and an extra export dependency. | Useful only when a current PDF already exists. |
| Structured SVG/canvas slide renderer | Strong control over identity and rendering at multiple scales. Very high complexity. | A broader product architecture change requiring restrictions or an HTML fallback. |

For scaled iframe previews, preserve a 1280 × 720 layout viewport and apply a visual scale. A 104-pixel-wide thumbnail uses approximately `104 / 1280 = 0.08125`, clipped into a 104 × 58.5 slot. A 104-pixel-wide iframe viewport can instead change responsive layout and text wrapping. Small visual size does not eliminate script, DOM, timer, or animation costs.

## Relevant precedents

- [Google Slides thumbnail API](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations.pages/getThumbnail): generated images addressed by page object ID. This documents the public API, not the editor's internal filmstrip implementation.
- [reveal.js overview implementation](https://github.com/hakimel/reveal.js/blob/master/js/controllers/overview.js): live slide elements positioned and scaled using CSS transforms.
- [Slidev rendering contexts](https://sli.dev/guide/global-context): explicit contexts such as `slide`, `overview`, and `previewNext` let content adapt its behavior.
- [reveal.js PDF export](https://revealjs.com/pdf-export/): explicit fragment policy for static output, including showing all fragments together.
- [Electron capture API](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts): native browser capture already available to this app.
- [html2canvas documentation](https://html2canvas.hertzen.com/documentation/): describes DOM reconstruction and its rendering limitations.
- [CSS Transforms specification](https://www.w3.org/TR/css-transforms-1/#transform-rendering): visual scaling without changing the underlying layout dimensions.
